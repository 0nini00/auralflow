# AuralFlow v0.7.5

这一版修的是「TX（QQ）源歌曲大量播放失败」：自定义源解析链恢复可用。根因是上一轮为避免并发过载而改成的「按顺序串行 + 每源 2.5s 预算」把正常耗时的脚本系统性击杀（实测走第三方代理的 flac 需 3.3s+），而失败提示只保留最后一个源，造成「显示内置 API 失败、没有走自定义源」的误读。本版把两个平台的自定义源解析都改为按序交错竞速，并修复了源内按档位串行等待会被服务端慢回退拖死的第二个缺陷。

## 修复（双端）

- **按序交错竞速替代固定预算**：`@lx/core` 新增 `raceStaggeredPriority`。候选按用户排列顺序启动：前一个结算立即启动下一个，未结算最多等 800ms 就并行启动下一个——顺序是「优先权」而非「独占权」，慢脚本不再被 2.5s 预算击杀，其后的源也不会被永久空等。
- **升级窗口保留音质追求**：首个达标结果开启 800ms 升级窗口，窗口内更高档或更靠前的候选仍可翻盘；命中本轮最高档且更靠前候选都已结算时立即定稿。
- **达标判定改为等级比较**：此前用严格相等，用户选 flac24bit 时源返回 flac 会被整源放弃；现在不低于本轮最低档即可参与裁决。
- **修源内慢回退拖死**：源内部按档位串行等待时，服务端对高清单走慢回退路径（实测 HYWmusic 的 flac24bit 请求 18.7s 才返回 320k 兜底，而 flac 只要 2.1s）会把整源拖死、真正可用的档位从未被请求。现在源内部同样交错竞速：高清单先发，未回在交错期后并发降档，可用的 flac 不再被慢档堵住。
- **错误聚合到每个源**：解析失败时列出每个源（含每个档位的原因，上限 500 字符），不再只显示最后一个源的「解析超时」。
- **阶段预算**：桌面端自定义源阶段总预算 8s、Android 端 7s（外层 12s / 10s deadline 与内置通道懒切预算均未改动），预算到期用已有达标结果定稿，没有才判失败。

## 测试与验证

- `pnpm test:all` 退出码 0：@lx/core 16 文件 192 例（新增竞速器 10 例）、桌面前端 65 文件 529 例（新增自定义源竞速回归 7 例）、移动端 617 例（新增 6 例）、Rust 74 例；双端 tsc、core typecheck 与移动端 eslint 通过。
- 回归用例覆盖：慢源 3.3s 不被击杀、最高档慢回退（18.7s）不阻塞降档、靠前慢源窗口内翻盘、窗口到期用后源定稿且迟到结果不覆盖、占位源快速失败立即启动下一个、全源失败错误聚合、快源命中最高档后续源零唤醒。
- 真机端点实测（HYWmusic 公益版，tx/倒影 003QrnHn2kR4FD）：flac 2.1s、320k 1.9s、flac24bit 18.7s（慢回退返回 mp3）——竞速器行为与该时序逐项对应用例。
- 顺带把两个移动端计时敏感用例的 runner 超时上限 5s 提到 20s：全量套件并发跑时它们实测 5.9-9.3s，此前偶发 batch 超时；断言本身未变。
- 发布后复验：7 个资产齐全、`releases/latest` 与 GitHub API latest 均返回 v0.7.5、两份更新清单与两条 update endpoint（gh-proxy 镜像 + 直连）逐字节等于本地构建产物、线上两个 APK 与本地校验过的包逐字节一致且各 21 个原生库齐全、`versionCode=31 / versionName=0.7.5` 由 `aapt` 核对。

## 边界与未做

- 超慢的高清单请求（如 18.7s 的 flac24bit 慢回退）在窗口外到达时不会被采用，但它仍在后台自然结束，不做主动取消（自定义源运行时无取消通道）。
- 外层 12s（桌面）/ 10s（Android）总 deadline 未改：竞速窗口下单源正常耗时已远低于该值，实测最坏组合（内置 API 无元数据 2.5s + flac 命中）约 6s 完成。
- **仍未做真机人工验收**：验证到自动化测试与打包为止。装好后建议实测：TX 源疑难歌曲（如「倒影」）能出流播放、设置里把 HYWmusic 音源开关切换后解析仍正常、播放条注记显示命中的自定义源名称。
