# 双端自定义音源与网关播放失败排查

日期：2026-11-20。代码基线：`4b66cf8`。本轮范围为原因定位；业务代码和已安装软件配置未修改。

已确认程序存在多条“某个源可用，正常播放仍失败”的路径。核心问题是候选链接在确认可播放前就结束选源，以及播放器拒收后不能继续尝试同一首歌的其他来源。最近的性能修改又引入了慢源被提前取消的回归。以下区分源码受控复现、安装软件日志和仍待确认的线索。

## 已确认的问题

### 1. P1：网关快速返回坏链接时，可用的自定义音源可能完全没有机会

位置：

- `desktop/src/services/playback/playbackResolver.ts:182`、`:499`、`:511`
- `apps/mobile/src/services/playerService.ts:513`、`:776`、`:793`

内置主源先执行，只要在等待窗口内返回达到音质门槛的 URL，就直接结束本轮选源。链接的探活和试听检查发生在这之后。若链接被判为 404 或试听片段，外层继续降音质，但没有保证先启动尚未尝试的自定义音源。

复现：让网关每个档位立即返回达档、但实际为 404 或试听的地址，同时配置一个一定能返回完整可播地址的自定义源。桌面与移动各验证两种情况，最终均失败，自定义源调用数为 **0**。

影响：用户启用多个源，也不等于播放失败前真正尝试过这些源。这条控制流在今日性能改动之前已存在。

修复方向：候选通过必要的可播放性检查后才能结束选源；主源被拒绝时，继续同一首歌的未尝试候选，并保留明确的失败原因。

### 2. P1：上一轮新增的超时策略提前取消可用慢源

移动端位置：`apps/mobile/src/services/playerService.ts:345`、`:357`、`:371`。

总预算 14 秒，主源耗满 2.5 秒，外层探活预留 6 秒，子阶段结算预留 0.1 秒，自定义源剩余约 5.4 秒。8 源、多档时再除以 4，**每次候选只有 1.35 秒**。该期限覆盖初始化、HTTP 排队、取链及候选探活。即使只有 1 个源，多档候选超过 3 个时也会除以 2。

桌面端位置：`desktop/src/services/playback/requestScheduler.ts:25`、`desktop/src/services/playback/customSourceBackend.ts:144`、`desktop/src/services/customSourceRuntime.ts:686`。

有候选排队时，调度器在竞争持续 3.5 秒后取消前面的请求，以释放名额。运行时还有同类调度层，所以单独可用的慢请求会因新增其他源而被取消。

使用真实编排源码、假时钟和模拟网络边界，结果如下：

| 场景 | 当前代码 | 对应优化前源码 |
| --- | --- | --- |
| 移动：同一源 3.3 秒返回，单源单档 | 成功 | 成功 |
| 移动：该源与另外 6 个慢源竞争 | 1.8 秒取消，失败 | `85752f9` 成功 |
| 移动：8 源、flac 四档降级链 | 1.35 秒取消，失败 | `85752f9` 成功 |
| 桌面：同一源 4.5 秒返回，单源单档 | 成功 | 成功 |
| 桌面：该源与另外 6 个慢源竞争 | 约 4.31 秒取消，失败 | `40f7583` 成功 |
| 桌面：8 源、flac 四档降级链 | 约 4.04 秒取消，失败 | `40f7583` 成功 |

移动端另验证了 1 秒取链、1.2 秒探活：单源成功，多源时在 1.8 秒取消探活，已取得的 URL 也被丢弃。桌面的探活取消可能被 `withBudget` 转成无结论并放行，不能把这条移动端结论直接套到桌面。

这组历史对照替换了对应编排及 limiter 源码，不是运行历史安装包。它证明最新修改引入了回归，不能解释所有旧日志。

修复方向：统一父截止时间与候选调度，保留真实并发限制，消除重复的抢占计时；按实际平台和音质能力构建候选。不能在仅有 5.4 秒、最多 3 并发时，承诺 8 个各需 3 秒的源都能完成，必须明确总预算与尝试策略的取舍。

### 3. P1：播放器拒收以后，没有可靠地换到同歌曲的其他来源

桌面位置：`desktop/src/stores/player/playbackPipeline.ts:248`、`:252`；`desktop/src/stores/player/engineSync.ts:113`、`:127`。

新解析出的地址如果被播放器拒收，只有缓存来源会进入重新解析分支；新鲜结果直接抛错。即使结果带有其他备用候选，该分支也不会逐个尝试。受控验证中，提供可用备用候选后，解析和引擎仍各调用一次就进入错误状态。

播放器运行中进入错误时会清 URL 缓存；满足自动跳过条件后，250 毫秒后切下一首。普通队列受设置控制，FM 有独立跳过逻辑，因此不能概括成“桌面所有错误都自动跳过”。

移动端位置：`apps/mobile/src/player/playbackService.ts:173`、`:182`、`:193`。

原生播放错误会清缓存并重解析一次，但调用中没有携带失败 URL 或来源排除信息。静态检查确认这一缺口；“再次选中同一快坏源”属于由该缺口产生的可达风险，本轮没有用真实手机重现具体歌曲。重试失败且自动跳过设置允许时，才会进入下一首。

修复方向：让当前歌曲的尝试过程保留已拒绝候选和剩余候选，在剩余预算内继续换源；只有候选耗尽或总预算结束后，才交给停止或自动跳过策略。

### 4. P1：快坏自定义源终止其他候选，重新竞速仍可能选回同一地址

位置：`desktop/src/services/playback/customSourceBackend.ts:291`；`desktop/src/services/playback/playbackResolver.ts:434`、`:519`、`:525`；`apps/mobile/src/services/playerService.ts:814`。

候选内层检查主要判定 HTTP 死链，试听判断在竞速结束后才执行。快试听源赢得竞速后，慢完整版源可能尚未启动就被取消。桌面端自定义源竞速 promise 还跨音质轮次复用：死链分支会清除它，但试听分支直接进入下一档，后续仍拿到之前的试听结果。

受控验证分别覆盖桌面和移动：快源返回试听，慢源能够返回完整歌曲，最终均失败，慢源未被调用。移动端试听分支虽已清空该 promise，但重跑没有排除刚才的坏候选，又被同一快试听源抢先返回。

桌面另复现一例：快源地址的探活返回 HTTP 522，被视为无结论，内外层均放行；第二个能够返回完整可播地址的源未启动。问题不在于必须把所有探活超时一律判死，而在于尚未确认可播就终止其他候选，之后又缺少播放器失败后的同曲换源。

修复方向：对明确拒绝的候选统一处理，不再复用其结果；死链、试听和播放器拒收都应继续消费剩余候选。

## 测试覆盖缺口

- `packages/core/src/custom-source/deep-test.ts:267` 的深度测试只取 URL 并检查 HTTP 格式，没有实际探活或解码；每次取链最多约 5.5 秒，也没有正式多源竞争时的 1.35 秒时间片。因此“测试通过”不能保证正常播放可用。
- 现有部分慢源测试未传真实播放 deadline，或仅使用单源，未覆盖“主源先消耗预算、多个脚本、多档、候选探活”同时出现的组合。
- 本轮定向验证使用真实源码与模拟网络边界，不执行用户安装的第三方脚本，不向第三方发送账号凭证。安装配置和日志仅作只读检查；报告不记录 Cookie、完整签名 URL 或脚本内凭证。
- 候选拒绝与播放器接管验证共 8 例：桌面 Vitest 5 例，耗时 8.34 秒；移动 Node 测试 3 例，耗时 4.72 秒。调度验证完成 16 项受控断言。每组命令均加 60 秒硬超时，一次性测试文件已清理。这些是对当前错误行为的复现断言，不表示漏洞已经修复。

建议修复顺序：先修主源拒绝后未启动自定义源与同曲换源缺口，再修最新调度回归，随后统一试听等候选拒绝分支，最后补充具有真实剩余预算的双端回归测试。
