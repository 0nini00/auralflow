# AuralFlow 移动端桌面一致性设计规格

日期：2026-07-14
状态：已确认，允许直接进入实施

## 1. 目标

移动端以桌面端为布局、视觉和业务功能的唯一参照，只保留以下平台差异：

1. 移动端侧边栏默认隐藏，通过前置抽屉打开。
2. 桌面系统能力使用 Android 原生等价能力替代，例如通知栏播放控制、系统文件选择器和系统返回键。
3. 响应式只改变尺寸、换行和触控密度，不改变信息架构，不隐藏业务功能。

完成后，用户在移动端应看到与桌面端相同的导航顺序、Header、内容结构、播放器能力、页面语义、主题、图标和业务入口。

## 2. 当前问题与根因

移动端已经具备默认隐藏的前置抽屉，问题不在抽屉本身，而在抽屉之外仍存在多套移动专用结构：

- 桌面壳为 `Sidebar | (Header / Content / PlayerBar)`，移动壳为 `Header / children / absolute MiniPlayer`。
- `RootStack` 与 `LibraryScreen` 内部状态分别维护详情导航，形成两个真相源。
- Header 在移动端只能显示菜单或返回之一，且 `AppChrome` 计算的返回状态没有进入 Header。
- 手机与平板分支会隐藏播放器功能，违反“仅侧边栏不同”的约束。
- 页面分别硬编码播放器底部补偿，造成布局、背景和滚动行为不一致。
- 移动端仍有文字方块 Logo、文本符号和 Emoji 图标，与桌面 Lucide 图标体系不一致。

因此本任务属于结构性修复，不采用逐页叠加样式补丁。

## 3. 方案比较

### 3.1 方案 A：逐页补样式

优点是改动小、单页见效快。缺点是继续保留重复导航、播放器分支和页面魔术数，后续桌面改动无法稳定同步到移动端。

### 3.2 方案 B：React Native 内结构性对齐

建立统一移动应用壳、统一详情导航和统一页面脚手架，再按桌面组件语义收敛各页面。保留 React Native 播放、文件、通知和手势能力。

该方案能满足视觉与功能一致性，同时保持现有原生能力，是本期采用方案。

### 3.3 方案 C：移动端嵌入桌面 Web UI

视觉代码复用率最高，但会削弱原生播放、后台服务、文件访问、通知栏和性能表现，并引入 WebView 与原生状态同步问题，不采用。

## 4. 总体架构

### 4.1 应用壳

新增移动端统一 `AppShell`，其结构固定为：

```text
MainDrawer
└── AppShell
    ├── AppHeader
    ├── ContentSurface
    │   └── ActiveScreen
    └── PlayerBar
```

- `MainDrawer` 继续使用 `drawerType: "front"`，初始状态关闭。
- `AppHeader`、`ContentSurface`、`PlayerBar` 始终处于同一布局流中。
- `RootStack.Player` 继续使用现有 `ImmersiveLyricsScreen` 作为沉浸式播放详情，但不再替代壳级 PlayerBar 的完整控制能力。
- 删除没有生产入口的旧 `PlayerScreen.tsx`，避免维护第二套播放界面。
- 播放器不存在时，内容区自然占满剩余空间，不保留空白占位。

### 4.2 导航单一真相源

`RootStack` 负责全部详情页和沉浸页面，`MainDrawer` 只负责桌面侧边栏对应的主页面。

```text
RootStack
├── MainDrawer
│   ├── Home
│   ├── Search
│   ├── Daily
│   ├── FM
│   ├── Playlists
│   ├── Downloads
│   ├── Local
│   └── Settings
├── ArtistDetail
├── AlbumDetail
├── PlaylistDetail
├── LocalPlaylistDetail
├── BiliCollectionDetail
├── LikedSongs
└── Player
```

`LibraryScreen` 等主页面只发出类型安全的导航动作，不再用本地 `subRoute` 条件渲染详情组件。系统返回、Header 返回、深链和进程恢复均读取同一导航状态。

### 4.3 页面脚手架

新增 `ScreenScaffold`，统一负责：

- 内容区背景、边框、圆角和透明度。
- 页面水平与垂直间距。
- 单一纵向滚动容器。
- Safe Area 与 PlayerBar 的布局关系。
- 加载、错误、空状态的页面级位置。

各页面删除 `paddingBottom: 100`、`paddingBottom: 120` 等播放器补偿值，不再各自推测壳层高度。

## 5. 组件设计

### 5.1 AppHeader

Header 与桌面端保持相同信息结构：

- 左侧为菜单、后退和前进操作；菜单是移动端额外入口，不替换历史操作。
- 中部为全局搜索，搜索词与搜索页状态同步。
- 右侧为主题切换。
- 详情页继续使用同一个 Header，不创建页面私有返回栏。

Android 系统返回优先关闭抽屉，其次关闭模态层，再返回上一导航记录。

### 5.2 AppSidebar

- 导航顺序和文案严格匹配桌面端。
- 设置和账号区保持在 footer。
- 使用桌面端真实 Logo 资产，不使用 `AF` 文字方块。
- 抽屉关闭后才执行主页面切换，避免残留遮罩或手势状态。

### 5.3 PlayerBar

移动端壳级播放器与桌面端保持同一功能集合：

- 当前时间、总时长和可拖动进度。
- 封面、歌曲名、歌手和添加到喜欢或歌单。
- 播放模式、上一首、播放或暂停、下一首。
- 音量或静音控制。
- 歌词入口和定时关闭。

窄屏允许分行、缩短文本和压缩间距，但不删除上述功能。所有图标按钮提供可访问标签和至少 `44 x 44` 的触控区域。

### 5.4 页面视觉原语

移动端建立与桌面语义一致的 React Native 组件，不直接导入 DOM 组件：

- `SectionHeader`
- `MusicCard`
- `SongRow`
- `DetailHero`
- `EmptyState`
- `LoadingState`
- `ErrorState`

桌面端是视觉真相源，React Native 组件使用同一主题 token、圆角、边框、间距、字体层级和 Lucide 图标语义。不得新增 Emoji 或文本符号充当图标。

## 6. 响应式规则

响应式只允许处理以下内容：

- 单列或多列排列。
- 控件换行。
- 封面、间距和字号的有限缩放。
- Safe Area、横竖屏和系统栏。
- 抽屉宽度与可滑动边缘。

响应式不得决定页面是否存在、功能是否显示、详情路由归属或业务操作是否可用。手机、平板和桌面使用相同的信息架构与功能清单。

## 7. 平台能力边界

以下桌面能力不直接移植到 Android：

- 系统托盘。
- 全局桌面快捷键。
- 独立悬浮歌词窗口。
- Tauri 窗口管理和桌面文件系统接口。

Android 使用现有或对应原生能力：

- 通知栏和锁屏播放控制。
- React Native Track Player 后台播放。
- Android 系统文件选择器。
- 应用内或系统允许范围内的歌词展示。

平台差异必须显式呈现，不通过静默回退伪装为桌面能力成功执行。

## 8. 数据流与状态

- 播放状态继续由移动端 `playerStore` 与 Track Player 持有。
- 导航状态只由 React Navigation 持有。
- Header 的前进按钮允许保存由 React Navigation 状态变更派生的路由描述记录；该记录只负责重放导航动作，不渲染页面、不持有页面状态，实际激活路由仍以 React Navigation 为准。
- 主题状态只由 `themeStore` 持有。
- 页面数据继续由相应 store 或 service 持有，不在 `AppShell` 复制业务状态。
- `AppShell` 只消费导航、主题和当前播放快照，用于组合布局。

禁止为桌面一致性新增第二份功能开关、导航映射或播放器状态。现有未被生产代码使用的独立 `sleepTimerStore.ts` 应删除，PlayerBar 只使用 `playerStore` 中的定时状态和动作。

## 9. 错误处理

- 导航目标无效时保留显式类型或开发期错误，不静默跳回首页。
- 原生平台操作失败时显示具体错误信息，不伪装成功。
- 页面请求失败使用统一 `ErrorState`，保留重试入口。
- 空数据使用统一 `EmptyState`，与请求失败区分。
- 播放、下载和文件选择错误继续由现有业务服务抛出并在界面边界展示。

## 10. 实施顺序

1. 建立壳层与布局契约测试，新增 `AppShell` 和 `ScreenScaffold`。
2. 收敛详情路由，移除页面内部详情真相源。
3. 统一 Header 与导航历史行为。
4. 将 `MiniPlayer` 收敛为完整 `PlayerBar`，删除旧 `PlayerScreen.tsx` 和重复 `sleepTimerStore.ts`。
5. 统一 Logo、图标、主题 token 和页面视觉原语。
6. 逐页对齐 Home、Search、Daily、FM、Playlists、Downloads、Local、Settings 和详情页。
7. 完成自动化验证、Debug 构建和 USB 真机验收。

每个阶段先写失败测试并确认失败，再实现最小代码使其通过。

## 11. 测试与验证

### 11.1 自动化验证

按以下顺序执行：

1. 壳层、导航、Header 和 PlayerBar 的定向测试。
2. `pnpm --filter @auralflow/mobile test`
3. `pnpm mobile:typecheck`
4. `pnpm mobile:build:debug`

Vitest 当前为 Node 环境，无法证明真实手势和视觉布局。测试应优先覆盖可提取的布局模型、导航映射、功能清单和源码集成契约，不使用测试专用生产接口。

### 11.2 USB 真机验收

设备必须先在 `adb devices -l` 中显示为 `device`。当前设备序列号 `TSP7MZ55FUHQUKSS` 显示为 `offline`，需要在手机端重新确认 USB 调试授权后继续。

真机验收至少覆盖：

1. 冷启动时抽屉关闭。
2. 菜单按钮和左侧边缘手势打开抽屉。
3. 遮罩点击和系统返回关闭抽屉。
4. 所有主导航项跳转后抽屉关闭。
5. Header 后退、前进、搜索和主题切换。
6. 手机横竖屏无水平溢出，功能不因窄屏消失。
7. PlayerBar 的进度、模式、上下首、播放、音量、歌词、定时和添加操作。
8. 各主页面、详情页、深链、下载、本地音乐和设置路径。
9. 通知栏控制、后台播放和系统文件选择器。
10. `adb logcat` 中无 `FATAL EXCEPTION`、`AndroidRuntime` 或未处理的 `ReactNativeJS` 错误。

## 12. 验收标准

满足以下全部条件才视为完成：

1. 除默认隐藏抽屉和平台原生能力外，移动端应用壳、导航、页面信息架构、视觉语义和业务功能与桌面端一致。
2. 手机与平板不再通过响应式分支隐藏功能。
3. 详情导航只有一个真相源。
4. 页面不再维护播放器底部补偿魔术数。
5. 移动端不再使用 Emoji、文本符号或文字方块 Logo 代替正式图标资产。
6. 定向测试、移动端全量测试、类型检查和 Debug 构建通过。
7. USB 真机验收全部通过，且运行日志无致命错误。

## 13. 风险

- 当前工作树包含大量未提交迁移改动，实施必须只触碰明确列出的移动端和文档文件，提交时逐文件暂存。
- 当前 USB 设备为 `offline`，不影响代码与构建阶段，但会阻止最终真机验收。
- 现有 Vitest 集成测试包含较多源码字符串断言，实施时应增加行为模型测试，避免只验证实现文本。
- 全页面视觉对齐范围较大，必须按壳层、导航、播放器、页面原语、逐页迁移的顺序推进，避免并行维护两套真相源。
