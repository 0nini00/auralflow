# 双端多音源播放修复

对应排查报告：`playback-source-diagnosis-2026-11-20.md`。修复基线为 `4b66cf8`，分支为 `codex/fix-source-playback-recovery`。

## 修复范围与不变量

这是跨模块的结构性修复。单独延长某个超时，或者在失败后再重跑相同竞速，都会保留“快坏源抢先返回”的根因。因此共同规则放入 `packages/core`，桌面和移动端分别连接本地网络、播放器与状态生命周期。

1. 候选进入竞速前检查死链与试听，结果分为已验证、无结论、拒绝。无结论的地址不能提前终止其他候选；已验证结果优先，音质和来源顺序在同类结果之间比较。
2. 网关、官方直连、自定义源和隐藏平台遵守候选判定；必要的探活结果随候选传递，避免竞速结束后重复探活占满预算。
3. 播放器拒收后继续同一歌曲的其他候选。当前尝试记录已失败 URL，以及来源、歌曲、请求音质组成的稳定候选标识；更换签名 URL 不会绕过排除。同一来源的其他音质仍可尝试。
4. 同曲失败恢复沿用既有截止时间。确实出现持续播放进度后，之后的网络故障才允许开启新的恢复窗口。手动切歌、暂停和停止继续使旧请求失效。
5. 并发上限保持 3。取得名额的候选拥有固定 8 秒，覆盖初始化、取链与探活；不按启用源数量缩短，也不因为出现排队者重复设置抢占计时。整条解析链最多 30 秒，候选通过时仍可提前结束。
6. 能力过滤由共享函数处理；已明确不支持当前平台或音质的脚本不占用取链名额。
7. 深度测试增加真实探活及试听判定，取链与探活共用 8 秒。404、试听与无结论不能再仅凭 URL 格式标成通过；实际解码仍由播放器验证。

## 验证计划

- 先验证修复前失败：网关 404/试听挡住自定义源、快试听/522挡住慢完整源、多源提前取消、新鲜地址拒收后没有换源。
- 定向回归增加稳定候选排除、同来源跨音质恢复、连续错误不续期、恢复位置不冒充健康进度、手动新意图取消旧恢复、严格并发与真实退出后归还名额。
- 按顺序执行共享核心及双端单元测试、类型检查与 lint、Windows/Android 构建、产物最小检查；单元测试命令硬超时 60 秒，完整测试按文件分组运行。
- 最后由未编写相应模块的代理交叉审查，并核对实际集成 diff。

## 行为边界

30 秒是失败链的上限，不是每首歌固定等待时间；它也不保证任意数量的脚本和音质都能尝试完。探活只验证资源请求与可判定的完整性，不能证明所有设备均可解码。第三方地址失效、服务器故障仍会明确失败，候选耗尽后才按现有自动跳过设置处理。

桌面请求头与 HTMLAudio 实际请求可能不一致，属于报告中的条件风险，本轮没有对应服务器实网证据，不将其声称为已修复。没有连接 Android 真机时，不把模拟边界测试称为手机现场播放验证。

## 审查补充

- 隐藏候选标识包含脚本、平台、平台歌曲 ID 和音质，避免一个聚合脚本在网易云或 QQ 的失败误伤其酷我/酷狗候选。
- 缓存失效等待纳入恢复的同一截止时间；挂起的清理不会无限阻塞手动切歌或恢复结束。
- 原生元数据才识别出的试听也进入同曲恢复。恢复失败时真实暂停播放器，不能只将界面改成停止。
- 暂停后续播重新绑定当前候选的恢复归属；恢复后确有进度推进，再次网络故障才允许开启新窗口。
